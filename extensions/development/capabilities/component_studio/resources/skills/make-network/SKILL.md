# 制作网络

先加载 `nexarbor-basics`。有当前网络时用 `inspect-network` 看总体和选中部分，再按需查看接口与配置。提问时用这套设计方法解释选型和接线，要求修改时继续制作。

## 工作路线

1. 写清目标行为与验收点：谁触发、谁处理、结果存哪、用户怎样看到结果。
2. `catalog_modules` 检索已有能力，读接口后决定组件与参数。优先复用通用组件；不同角色、地点和团队用前端配置区分。
3. 用 `node_template` 取合法骨架，装配模块与工具，设计频道、强度、信号和亚节点。让实际拓扑表达协作，避免把固定节点顺序硬编码进模块。
4. `network_patch` 分批写候选网络及文本。需要时复制当前网络，在测试副本中验证可达性、信号与数据效果；正式网络保持独立。
5. 缺少通用能力时，用 `request_component` 给模块／工具 Agent 描述能力和接口需求；等它验证发布，再组装。优先复用已有组件，避免不必要的委托。
6. `validate` 检查网络与依赖，验证满足需求后交付预设与简洁中文说明。不要生成多余启动器或绕过框架的胶水。

信号、可达性、亚节点、上下文和锁从 `nexarbor-basics` 的相应参考读取。具体模块参数以 `inspect_modules`、发布文档和 Schema 为准。

正确示范：一套服务模块配不同参数，沿道路分发访问权限；角色并行活动。反例：先串起所有 NPC，再让每个模块按预设节点 ID 调下一位，用大锁掩盖并行问题。

用户只是提问时先回答；要求修改时在保留历史的工作分支中继续，不必另开角色或切换权限。

## Git 和进度

用 `project_git` 查看状态、分页差异和提交历史；需要时提交、配置用户提供的远程地址、推送或恢复。`restore` 会先提交当前进度，再从指定提交建立恢复工作分支，继续使用当前对话。用户要求上传时调用 `push`，不强推。恢复的是制作候选，正式运行网络仍由客户端的应用流程更新。
