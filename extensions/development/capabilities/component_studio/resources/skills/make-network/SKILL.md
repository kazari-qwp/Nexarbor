# 制作网络

先加载 `nexarbor-basics`。有当前网络时用 `inspect-network` 看总体和选中部分，再按需查看接口与配置。提问时用这套设计方法解释选型和接线，要求修改时继续制作。

## 运行中管理员与项目制作

宿主说明当前是“运行中局部网络管理员”时：使用已有预设和组件完成增删节点、人数配置和接线；用 `inspect_nodes` 或 `view_network` 查看一次，确认实例和入口已经出现，然后提交。无需重测预设内部逻辑，不编写行为测试、不模拟成员执行；下文项目制作的自测与交付流程不适用于这个分支。格式、授权和版本由保存/提交程序检查。

以下路线适用于制作新项目或修改业务实现的网络制作 Agent。

## 工作路线

1. 写清目标行为与验收点：谁触发、谁处理、结果存哪、用户怎样看到结果；保留用户要求的可调参数、重复使用与恢复行为。
2. `catalog_modules` 检索已有能力，读接口后决定组件与参数。优先复用通用组件；目录注明旧版或反例的组件仅供分析，不作为新设计的默认方案。不同角色、地点和团队用前端配置区分。若接口迫使模型手工搬运大段原文，把缺口提成小组件，不能用更长提示词补上。
3. 用 `edit_network` 的短命令创建节点、按发布默认值装模块、接线和写文本。需要时才取完整骨架或整节点替换。让实际拓扑表达协作，避免把固定节点顺序硬编码进模块。
4. 分批组装并按需查看候选。确认一条关键路径后尽早写成自动用例，后续扩展时重跑，避免几十次交互调用后才开始自测。需要时复制当前网络，在副本中验证可达性、信号与数据效果；正式网络保持独立。
5. 缺少通用能力时，用 `request_component` 描述能力和接口需求；等它验证发布，再组装。已有委托未完成或需修订时用 `task` 继续其工作，不从空白重做；运行中追加会在原任务与预算内处理，查看回执中的已投递／排队／未投递，不能把“任务仍在运行”当成已接收；发布后的修订使用新模块 ID，按返回接口装配。优先复用已有组件，避免不必要的委托。
6. 把关键行为写成可重复的测试；`validate` 同时检查网络、依赖并运行 `tests/test_*.py`。测试要检查真实消费结果和失败后的状态，不只检查返回字典。对照原需求逐项验证再交付预设与简洁中文说明；遇到框架限制先按需查相关参考或补组件，不用未实现清单替代用户要求。
7. 强烈建议阅读小镇案例分析，并查看完整案例本身：分析见 `nexarbor-basics` 的 `references/lessons/13-town-evolution.md`；完整初始项目在 `<安装目录>/resources/examples/npc-town/`，加载 `inspect-network` 后用 `project` 路径按需研究；应用模块从该项目的 `nexarbor.json` 定位，不假定核心组件目录提供同名实现。

正确示范：同类地点复用相同模块，用配置区分商品、资源和费用；不同职责通过模块组合与接线协作，角色并行活动。反例：用固定串行 tick 链掩盖长事务造成的互相等待，再把这种顺序固化为应用逻辑。

用户只是提问时先回答；要求修改时在保留历史的工作分支中继续，不必另开角色或切换权限。

## Git 和进度

用 `project_git` 查看状态、分页差异和提交历史；需要时提交、配置用户提供的远程地址、推送或恢复。`restore` 会先提交当前进度，再从指定提交建立恢复工作分支，继续使用当前对话。用户要求上传时调用 `push`，不强推。恢复的是制作候选，正式运行网络仍由客户端的应用流程更新。
