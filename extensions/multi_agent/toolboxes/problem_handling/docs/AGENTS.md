# 问题处理流程

进入 handle_problem 表示开始处理问题，不表示当前委托必然阻塞，也不增加业务权限。先识别自己的委托和验收要求：问题是否修好、委托能否交付是两个判断。

## 入口与问题归属

填写 problem 和 origin：self 为自身问题；subordinate 为下属问题，同时填写真实 origin_node_id；dependency 为依赖问题，已知来源节点时填写 origin_node_id。归属用于说明来源和处理责任，不授予对该节点的访问或管理权限，不限制只有自身问题才能进入。

继续同一个未解决或中断的问题时填写原 problem_id，保留累计尝试和结束记录；不要换个描述新建问题以清空记录。收到下属报错并不自动要求进入排障：若当前委托只是记录、评估或汇总结果，可直接正常汇报真实失败。

## 排障与三个出口

需要排障时先 experience_query 查询经验线索，必要时 incident_query 补充。待审核经验不代表可靠。用 problem_attempt 指定查询到的 experience_id 后，在原有权限内验证。只有 allow_self_repair=true 才能不填 experience_id 开始自行修复。简单参数错误可按任务约束正常重试。

1. **已解决：problem_resolved。** 必须有实际工具验证和具体依据。自行修复成功须先 experience_submit 提交候选经验，再关闭问题。继续原任务。
2. **未解决，结束本次处理：problem_defer。** 当前委托仍能继续或允许交付失败结果时使用。填写 reason（为什么结束）、impact（仍未解决的问题及影响）、continuation（为什么仍可履行委托以及如何继续或交付）。可在开始修复前判断后退出，无须为退出伪造查询或尝试。保留问题和累计尝试，不标记解决、不记成功经验、不向上发送阻塞、不结束当前任务。继续正常流程，最终汇报须保留相关失败和影响。达到任务规定的尝试上限或移交处理也不能隐去失败；若自身委托因此无法完成，选择第三个出口。
3. **当前委托阻塞：datanet_feedback。** 必须先查经验；有自主排障授权时按既有规则进入尝试分支。必填 task_blocker，说明为什么该问题使自己当前受托任务无法继续或交付。missing_tool 固定“工具缺失”，permission_denied 固定“权限不足”；other 才填最多80字的 message。框架保存说明、附自身ID、通知创建者并停止当前轮。不能仅因为下属报错就把同类错误作为自己的阻塞上报。

没有自主修复授权或修复失败时，根据当前委托能否继续，在第二、第三个出口之间选择，不一律上报。问题还在 active 状态时必须先选择出口；退出排障不等于任务成功。

## 例子

委托是“运行一次测试，成功或失败都记录并归档”：操作者缺终端工具可能阻塞它的执行任务；协调者收到失败且归档完整，仍可交付测试失败报告。若协调者已进入排障，用 problem_defer 后正常返回记录。

委托是“必须完成文件生成”：缺工具使必要产物无法生成，且没有获准替代方式，不能通过 problem_defer 声称完成；应说明自身委托受阻并上报。

退出后临时排障工具撤下。未解决退出的问题及影响持续保留在上下文和持久记录中，重启后也可查见；重新处理使用原 problem_id。成功经验的审核与提升规则保持不变。
