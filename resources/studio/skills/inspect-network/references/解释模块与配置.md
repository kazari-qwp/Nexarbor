# 解释模块与配置

问题是“为什么这里需要这个模块”，先看其所在节点的职责、执行入口和相关接口，不必遍历所有节点。

```json
{"nodes":["N3","N8"],"section":"summary"}
{"nodes":["N3","N8"],"section":"modules"}
{"modules":["example.reader"],"section":"interface"}
{"nodes":["N3"],"section":"config","modules":["example.reader"]}
```

以上分别传给 inspect_nodes / inspect_nodes / inspect_modules / inspect_nodes；模块 ID 以真实查询结果为准。节点批量上限12，模块上限8。节点的子节点模块表单列，不能把父子模块当成同一张装配表。

需要验证运行现状时另查 `section:"state"`。大配置或状态用 `fields:["目标顶层字段"]`；返回 large 表示需要缩小字段，不代表内容不存在。执行访问范围和预处理绑定在 `section:"settings"`；参数默认值在 inspect_modules 的 config_schema。

选择组件用 modules，fields 填该组件内部的字段名，不填模块 ID。返回 missing_fields / available_fields 表示字段未匹配，不能解释成模块状态为空。

接口不足以解释行为，再 `read_resource(module="真实模块ID")` 列文件，按需读取 README 或 module.py 的相关行。每次最多300行。网络内的文本用 `read_network_text` 列路径，再指定 file 按行读；查看磁盘项目时也可按行读取其网络清单、节点文件和模板；返回的内容固定在该项目快照中，不执行项目代码，也不读取项目外文件。

正确：用接口、实际配置与相邻关系解释这个装配能起什么作用，区分事实和对设计意图的推断。

反例：把 initial 当当前余额；因模块不在父节点表中就说不存在；为解释一个参数读取全网所有状态与全部源码。
