# 先判断是否需要锁，再锁、重查、操作、解锁

**先问：其他访问看到执行到一半的数据，具体会违反什么约束？** 没有这样的中间状态就不加事务锁。

反面教材：小镇曾把普通读取、免费发信和整轮模型活动也锁住，再用串行 tick 链掩盖等待。不要照抄。普通读取、同步本地批改和免费投递不额外锁；双向位置更新、余额和库存一起变化才用短事务。收费发信只保护扣费与入箱，不保护思考和回应。

具体模块在构造器声明 transaction 参数，宿主注入原节点事务端口；只锁已通过 access 到达且涉及本次修改的节点：
```python
@access(channels=['ledger'])
async def transfer(self, node, amount):
    async with self.transaction([self._access_origin.info.node_id,
                                 node.info.node_id], timeout=20):
        # 锁内重查余额、库存、旧位置，检查后完成修改。
        await node.modules.get('账户模块').debit(amount=amount)
```
已有访问先结束，锁定节点仍可达，其他调用与信号等解锁后继续。持锁者转调可重入同一事务，不能扩大集合。锁后备份节点状态、出边、工具/模块、数据文件、Agent 输入及原生日志位置；正常退出提交，异常/取消恢复。

反例一：在 with 内返回 error 属于正常退出，会提交；应让异常穿出事务。反例二：锁前检查位置，等锁后直接改；前提可能已变，必须重查。

移动通常锁 NPC、旧地点和新地点；交易还包括执行库存模块的服务节点。不要锁整个网络，也不要把普通出边操作误当作已包住余额和访客更新。

**事务保护中间状态的可见性。** access 到节点时等待该节点解锁，再读取其当前出边；改边前安排后续操作及查询顺序，像操作单链表一样谨慎，并注入末尾失败验证整组恢复。不在已经拿到节点后重复检查可达性。

不要持独占锁等待模型、独立信号、终端或外部网络。外部效果不能靠内部备份回滚；先提交待办，再做带幂等身份的外部动作，下次核对继续。嵌套锁只能重入已有集合。

共享外部资源要求跨调用互斥时，先登记可恢复的占用/任务身份；等待期间不持节点事务，回来后核对身份与结果。一次调用内顺序 await 不代表两个调用不会交错；测试要让第二次在第一次等待时到达。

幂等键应区分 self.module_id、所属节点 ID、原请求者、业务 key 和步骤；不能只用用户 key。否则同一人在两家商店使用同 key 可能少扣费。测试覆盖两个实例与两个请求者复用同 key。
