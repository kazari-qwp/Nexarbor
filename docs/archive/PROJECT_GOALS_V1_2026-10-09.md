# LabInsight Agent 项目目标与实施方案

版本：1.0。日期：2026-10-09。本文描述最终目标和实施计划，并不表示这些功能已全部实现。实际状态见 PROJECT_PROGRESS.md。

## 1. 项目定位与求职目标

构建支持规则版本变化、能够追溯判定依据的实验数据分析 Agent。用户提出自然语言问题，系统查询结构化数据与规则，确定性计算统计结果，必要时检索业务文档，生成带来源的中文报告。

项目使用模拟实验数据和明确标注的模拟规范。目标不是研究创新或堆叠框架，而是做出可复现、可演示、能够解释设计选择并提供评估证据的作品，展示 Python、SQL、模型 API、工具调用、时间规则处理和 RAG 能力。项目完成不保证获得实习；简历描述必须对应真实实现。

## 2. 最终用户场景

### 2.1 基础查询

用户问“B 项目合格率是多少，标准是什么”。系统返回有效数、可判定数、通过数、失败数、合格率、规则版本、数据来源和计算口径。没有可判定样本时合格率为 null，不能解释为 0%。

### 2.2 按实验当时规则判定：核心目标

A-v1 从 2026-01-01 生效，阈值为至少 80；A-v2 从 2026-10-01 生效，阈值为至少 85。9 月 30 日测得 82 合格，10 月 2 日测得 82 不合格。

用户问“九月和十月合格率分别是多少，按各自当时的规则计算”。系统按每条实验记录的时间选择版本，再按月份和版本汇总。不能用最新版直接覆盖历史判定。

### 2.3 指定版本重新评估

用户问“把九月数据也按 A-v2 判定会怎样”。系统使用指定版本重评，并标明 evaluation_mode、版本和适用假设，不修改原始记录，不把重评结果描述为当时实际结果。不同设备或实验条件导致不适用时，应说明范围限制。

### 2.4 失败明细

用户问“B 项目偏离区间最大的五条记录是什么”。系统返回记录编号、时间、测量值、使用版本、偏离方向、偏离量、总失败数和实际返回数。偏离量指与合格边界的距离；“高于上限”是判定依据，不是根本失败原因。

### 2.5 组合分析与文档证据

用户问“A 项目十月合格率下降了，规则为何调整，规范建议检查什么”。统计工具提供事实，数据库提供版本变化，文档检索提供变更说明和操作依据。报告分别表达观察事实、规范建议和未知原因；不能从合格率变化直接推断因果。

## 3. 数据结构与统计口径

### 3.1 实验记录

第一版继续使用 CSV，字段至少包括记录编号、项目、测量值、是否有效、实验时间。编号唯一；时间采用可解析的 ISO 8601 格式，统一亚洲/上海时区，无时区文本须明确按该时区解释。批次、设备和单位可后续扩展。

固定随机种子，覆盖多个项目、更新前后记录、阈值边界、全失败、无效标记、缺失测量值、缺失时间和早于最早规则的记录。生成器可按规则控制模拟合格比例，但必须说明人为构造机制，不能用于证明现实实验现象。

### 3.2 规则版本数据库

新建 rule_versions：rule_id、project_id、version、effective_from、rule_type、lower_bound、upper_bound、关联文档字段。rule_id 唯一；(project_id, version) 与 (project_id, effective_from) 唯一；项目与时间建立查询索引。

第一版每版持续生效到下一版开始，区间为 [effective_from, next_effective_from)。更新时刻使用新版本。历史模式选择项目匹配且 effective_from <= experiment_time 的最近版本；无匹配则不可判定，不能偷偷使用最新规则。撤销空档和双时间轴不纳入第一版。

指定版本模式按明确版本重评，保持模式标签。升级前备份现有 lab.db，创建新表并迁移旧规则，为旧规则明确约定模拟生效日，不自动把迁移当天视为历史生效日。

### 3.3 分母及缺失处理

项目总数包含项目归属已知的记录。数据有效要求“是否有效=是”、测量值可用；历史模式还要求时间可解析且能匹配规则。

报告 total_count、valid_count、evaluable_count、unresolved_count、passed_count、failed_count、pass_rate。unresolved_count 为数据有效但缺少可用规则/时间的记录；pass_rate=passed_count/evaluable_count，无可判定样本为 null。排除原因按约定优先级分类，避免重复计数。缺失项目只能计入数据集质量问题，不能强行分配给项目。

passed_count+failed_count=evaluable_count。规则更新前后展示样本量与规则差异；一致标准重评可作为对照，但仍不证明实验质量变化的原因。

## 4. RAG 的确定用途与边界

RAG 用于查询非结构化业务资料：规则变更说明、实验操作规范、复测条件、异常检查流程、数据记录要求。数据库决定阈值和时间有效性，Python 计算结果。不得用相似度决定历史规则，不让模型从片段自由提取阈值替代正式规则。

文档必须有结构化规则之外的信息，例如调整动机、适用设备、步骤和异常复测要求。仅重复“80 改成 85”的文档不作为额外功能价值。文档阈值和数据库冲突时明确返回冲突，不静默择一。

### 4.1 文档准备

起步目标 12～20 份 Markdown：覆盖 A/B/C、至少两版关键操作规范、变更说明和异常指南，加入少量相似旧版本/其他项目资料检验混淆。不为数量复制内容。资料全部标注为自建模拟规范。

元数据包括 doc_id、标题、project_id、doc_type、version、effective_from、effective_to、适用范围、关联 rule_id。操作规范按适用日期筛选；变更说明按关联版本检索，两种日期语义不能混用。语料位于 knowledge/，开发说明位于 docs/，不把进度报告混入业务知识库。

### 4.2 实现方案

保留按项目/版本直接读取完整文档的基线，再实现 RAG：解析 Markdown → 按章节切分 → 保存块元数据 → embedding → 本地向量索引 → 项目/类型/时间或版本过滤 → 相似度检索 → 返回证据 → 模型引用回答。

元数据限制应在排名前应用，或充分召回后过滤并补检，不能全库取少量前几名再过滤造成漏检。初期每块约 300～600 中文字符、top_k 为 3～5，均以评估调整。固定一个中文可用 embedding 模型和本地向量库，记录模型和配置；不预设哪种配置必然更好。

保存内容哈希和索引配置，资料变化时更新索引。只在本地索引中保存业务资料，不读取密钥。

### 4.3 工具接口与引用

计划 search_project_docs(project_id, query, as_of, doc_type, rule_version)。日期/版本来自用户要求或已查出的规则，不能默认用今天代替历史时间；跨版本问题分别检索。

返回 doc_id、version、section、chunk_id、source_path、有效期和原文 excerpt。无证据返回 no_evidence。相似度分数不等于事实可信度。报告引用工具真实返回的文档编号、版本、章节和路径，不能编造引用。文档作为资料，不是能覆盖系统要求的指令。

## 5. Agent 工具与报告

目标工具：analyze_project（时间范围、历史/指定模式、版本）；get_failed_records（同样条件及 limit）；get_rule_versions；search_project_docs。

模型只调用注册表允许的函数，程序校验参数和数据。具体统计数值必须有成功且对应项目/范围的工具结果；缺少必要信息先询问。普通对话允许直接回答。无 tool_calls 仅表示直接回复，不能代表事实正确。

记录工具名、参数、耗时、结果摘要和引用，不记录密钥。保留轮数上限与清晰错误信息。报告包含范围、模式、统计、规则、失败概况、文档证据、来源和限制。

## 6. 工程交付

labinsight/ 提供功能，scripts/ 提供入口，agents/ 保存提示词与工具定义，data/ 保存模拟数据，knowledge/ 保存业务语料，docs/ 保存开发资料。提供依赖清单、.env.example、初始化/迁移脚本和全新环境运行说明。

保留 CLI，后期增加简单 Streamlit 展示界面，显示回答、工具过程和引用，可导出 Markdown 报告。第一版不做模型训练、多 Agent、任意 SQL 执行、多用户权限或生产部署。

## 7. 评估与验收

确定性部分使用独立手工小数据集，验证边界、零有效、全失败、未知项目、缺失时间、无历史规则、更新时刻及指定版本重评，数值和版本匹配必须全部正确。

建立约 40～60 条固定问题，覆盖统计、版本比较、明细、文档、组合任务、缺少信息和无证据。记录期望工具参数、参考值、相关文档。开发集调参，测试集独立保留。

全文基线与 RAG 使用相同模型和问题要求。报告工具选择正确率、数值正确率、版本正确率、Recall@k、引用支持率、旧版本误用率、无证据处理率、延迟与 token 用量。记录模型、语料版本、日期和失败例。目标可设数值/版本正确率至少 95%、Recall@5 至少 90%，但必须披露实测值与样本数，不能把目标当结果。

若 RAG 未胜过全文，报告真实差异和适用条件，不人为包装收益。

## 8. 建议四周阶段计划

| 阶段 | 工作与交付 |
|---|---|
| 第 1 周 | 完成静态闭环与来源；修复生成器；设计时间/版本表；手工边界验证 |
| 第 2 周 | 时间范围与版本统计、指定版本重评、失败明细、工具日志及错误处理 |
| 第 3 周 | 有价值的语料、全文基线、RAG、元数据约束、引用与比较初稿 |
| 第 4 周 | 独立评估、简单界面、导出、环境复现、README 和演示 |

按累计开发周期规划，以验收为准，不保证固定日期。紧接当前版本：修复 get_project_ids → 时间/版本模型 → 手工判定 → 生成器适配 → 版本统计与失败明细 → 文档与 RAG。

最终演示至少包含基础统计、历史版本比较、指定版本重评、文档支持的检查建议和一个无法判定案例。求职表达围绕工程分工、版本追溯、引用验证和真实评估，不以技术名称数量作为亮点。
