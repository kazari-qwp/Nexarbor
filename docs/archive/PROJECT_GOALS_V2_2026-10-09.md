# 可组合的 Agent 记忆与数据访问系统：项目目标与实施方案

版本：2.0。更新日期：2026-10-09。本文是后续工作的统一目标依据；实际完成情况见 [进度报告](PROJECT_PROGRESS.md)。旧实验分析方案保存在 archive/PROJECT_GOALS_V1_2026-10-09.md。

## 1. 项目定位与本次范围调整

构建一个可组合的 Agent 记忆与数据访问系统：每个节点最多保存一种本地数据类型，可以没有本地数据，可以选择是否带 Agent；通过强弱接口、读写权限和统一工具组合成网络。系统支持精确事实查询、长资料检索、会话摘要和任务恢复，后期允许 Agent 自主创建节点和调整存储组织。

设计灵感来自 Minecraft Applied Energistics 的接口与存储总线。采用“简单组件＋明确连接规则”形成复杂能力。底层使用现有数据库、文件和向量索引，不开发新的存储引擎。

当前仓库名称 data-analysis-agent 和 labinsight 包暂时保留，不急于改名。LabInsight 实验分析作为第一个接入模块和场景验证，已有 CSV、SQLite、统计和工具循环继续复用。项目主线从实验报表扩展为记忆/数据网络；历史规则判定保留为应用验证功能，暂不作为开工第一步。

求职交付是一套能运行、解释设计、量化效果并展示失败边界的系统。重点能力：Python 模块设计、持久化、工具调用、检索、记忆更新、权限、图遍历和评估。

用户已确定：Agent 自主创建数据库是最终目标，留到最后实现。前面各阶段使用预先定义或人工配置的节点，不通过提前删掉该功能缩小最终范围；核心演示可先交付，最终自治阶段另行验证。

## 2. 核心设计原则

### 2.1 单一数据节点和组合节点

“最多一种数据”指本地数据的类型/schema，不指最多一种检索算法。具体类型例子：精确事实、文档、会话摘要、任务状态、原始事件、实验记录、实验规则。一个事实节点可以同时支持精确 get 和条件查询；文档节点可以有关键词/向量策略，仍是同一文档类型。

无数据节点只能组织接口和能力。需要多种数据时，将多个单一类型节点通过强接口连接到组合节点。所有节点从外部遵循同一协议。节点是逻辑空间，不必每个节点创建一个数据库文件；初版可在 SQLite 中按 node_id 隔离存储。

同一原始输入可以生成多种表示，存入不同类型节点：一段对话中联系方式进入事实节点、进展进入任务/摘要节点，原始消息进入事件节点。各表示保留来源引用，不强行只选一处。

### 2.2 数据和 Agent 分离

节点可配置 agent=null；查询和写入照常可用。简单任务由确定性工具完成，需要规划、提取或解释的节点才启用模型。数据组合不要求每一步经过 Agent。

多个节点逻辑合并不自动合并 Agent 身份、提示词或会话历史。首版仅根 Agent 必需，验证一个可选子 Agent 的接口即可；是否增加更多依据评估决定。

### 2.3 组合示例

```text
用户/任务入口：无本地数据，带根 Agent
├── 强接口 → 精确事实节点（SQLite）
├── 强接口 → 资料节点（原文＋索引）
├── 强接口 → 会话摘要节点
├── 强接口 → 任务状态节点
├── 强接口 → 原始事件节点
└── 弱接口 → 外部或独立项目节点

LabInsight 项目入口：无本地数据，Agent 可选
├── 强接口 → 实验记录节点
├── 强接口 → 实验规则节点
└── 强接口 → 实验规范节点
```

## 3. 节点、接口和访问语义

### 3.1 节点配置

至少包含 node_id、name、description、data_kind（无数据为 null）、schema_version、backend、retrieval_config、agent_config（可空）、本地工具清单和生命周期状态。节点配置可持久化，重新启动后网络可恢复。

业务主键与全局身份分开：事实可按 (subject_id, key) 查；全局结果用 (owner_node_id, record_id, version) 定位。不要根据文本相同就删除不同来源的合法记录。

### 3.2 有向接口

至少包含 interface_id、source_node_id、target_node_id、strength（strong/weak）、read_allowed、write_allowed、允许的数据类型/工具、过滤条件、priority、是否允许继续转发和 enabled。

A 持有到 B 的接口，不意味着 B 自动持有反向接口。父子管理关系与数据访问关系分开：初版管理关系树形，访问图可有环；避免多方管理的删除和归属歧义。

### 3.3 访问范围：保留用户定义

- 本体访问 local：只访问本地数据，不遍历接口。
- 弱访问 integrated：本体＋沿强接口可达的授权数据空间。
- 强访问 federated：本体＋强弱接口可达的授权数据空间。

强访问增加查询范围，不增加操作权限。每次转发都验证接口、目标和调用者权限，拒绝通过中间节点扩大授权。初版对每条边显式配置允许转发，默认不自动把第三方数据暴露给上游。

### 3.4 双向强连接的逻辑合并

在接口开放完整默认空间、没有相互矛盾过滤且调用者权限相同的情况下，双向读写强连接节点对调用方近似一个数据库：从任一入口可见同一组数据，并可路由写入。进一步把强接口的相互可达节点（强连通分量）视为逻辑组件。

有过滤或权限差异时仍保留各入口视图，不盲目合并。合并是联合命名空间和访问语义，保留所有者与来源；不承诺不同底层数据库共享事务，也不把各 Agent 的历史自动合并。

### 3.5 防循环与预算

先由确定性网络层计算授权范围，再查询节点，不依靠 Agent 互相递归发现网络。为请求分配 request_id，对相同子查询、权限上下文和访问模式去重；不同子查询可再次访问同一节点。结果按全局身份去重。

配置最大深度、节点数、结果数、模型轮数、耗时和上下文预算。超限明确返回截断/部分结果与原因，不能伪装成完整查询。接口改变后更新或失效缓存。

## 4. 统一操作协议与写入路由

目标操作：describe（能力/schema）、query、get、insert/upsert、history、list_tools、invoke_tool。可选 invoke_agent 与网络配置操作分开暴露；不适用操作明确返回 unsupported。

统一结果封装包含 status、request_id、items、sources、truncated、errors 和统计信息。items 保留 data_kind、owner_node_id、record_id、version、内容和时间。sources 包含原始消息/文件、节点、记录、检索路径及内容哈希或版本。不同检索器的相似度分数不能直接当统一可信度排序。

模型工具以 node_id＋tool_name 命名，防止多个子节点同名工具碰撞。Skill 可以保存查询流程和操作说明，但执行始终经工具及运行时权限检查；加载 Skill 不代表获准写入。

写入策略：更新已有记录写回拥有者；插入依据数据类型、过滤和优先级选择可写目标。同一优先级存在歧义时按确定规则或询问，不随机选择。默认不向所有连接复制数据。无目标先返回 no_destination；只有最终自治阶段才允许提出/执行创建节点。

存储事实与摘要之间不要求跨库原子事务，但精确事实提交后必须同步标记派生摘要/索引为过期。异步更新失败可以重试；旧摘要不能继续作为已更新事实的权威来源。

## 5. 记忆场景：首版必须完成

### 5.1 精确事实

使用模拟用户和模拟联系方式，保存 subject_id、key、value、version、来源事件、recorded_at、有效时间/状态。手机号等作为字符串，按身份和字段精确查询，不能靠语义相似度猜数值。

支持当前值和历史值。重复输入同一事实不产生多份当前值；用户明确更正产生新版本；不明确冲突保留来源并标记需要确认，不自行编造结论。提取结果经过 schema 校验。

### 5.2 长资料与 RAG

文档节点保存原文、版本和索引。RAG 用于设备手册、实验规范、项目资料和规则变更说明的证据查询。项目目标文档是开发依据，不自动混入业务知识库。

先准备约 10～20 份明确标注的模拟业务文档，覆盖多个项目、相似旧版本和不适用资料。按章节切分，保存 doc_id、project_id、version、有效期、section、chunk_id、来源和内容哈希；建立 embedding 与本地向量索引。保留关键词/全文基线，首版不要求一次接入多个向量库。

查询先限定授权节点、项目和适用版本/日期，再检索；返回原文片段、版本和来源。无证据返回 no_evidence。历史规范按日期过滤，变更说明按关联版本检索。RAG 不负责选取可执行规则、计算统计、确定精确联系方式或授权权限。

摘要可以帮助定位文档，但结论回到原文证据。文档变更更新/失效索引。文档与正式数据库规则矛盾时提示冲突，不静默替换。

### 5.3 会话摘要

保留原始对话事件，摘要保存覆盖范围、关键约束、决策、未完成事项和来源引用。最近少量原始消息＋适用摘要组成会话上下文。摘要按范围更新，不在每轮随意重写整个历史。

摘要是压缩表示，可回查原文；任务状态和精确事实有独立节点，不只埋在自由文本摘要里。更新事实时摘要引用的旧版本须标记过期。

### 5.4 任务恢复

保存 goal、status、completed_actions、pending_actions、相关资料、updated_at。新会话/新 Agent 可读取恢复任务。完成状态由可验证操作或明确用户输入支持，不能只因模型说完成就更新。

### 5.5 自动归档与上下文组装

首版节点类型人工预定义，Agent 可以自动选择既有节点并提出结构化写入计划，再由程序验证执行。这与自主创建数据库是两个阶段，不能一开始混在一起。

读取时根据问题选择精确事实、任务状态、摘要和文档证据，在指定 token 预算内组装上下文。先实现固定策略，再评估模型路由；保留可观察的选取/舍弃记录。

## 6. 最后阶段：Agent 自主创建数据库/节点

此功能明确安排在核心网络、记忆更新、RAG、权限和评估稳定之后，作为最终阶段实施；不提前启用。前面完成的系统不依赖它。

创建指逻辑节点/命名空间，必要时分配底层存储，不要求每次创建物理文件。触发候选包括新项目/用户隔离边界、现有节点不接受的数据 schema、资料规模导致需要拆分；不是每遇见一条新事实就建库。

步骤：诊断目标 → 生成计划（新节点类型、归属、schema、接口和路由、迁移范围）→ 程序校验 → 创建并记录日志 → 写入/迁移 → 验证查询等价和权限 → 失败回滚或保留明确可恢复状态。

约束包括节点数、创建频率、深度、模型和存储预算、重复检测及幂等键。新接口不得扩大原权限；已授权写操作可执行，其余操作按应用设定的确认策略处理。记录创建理由、前后指标和每条迁移数据来源；不静默删除原文。

最终验收：缺少目标时能合理创建一次节点，重复相同请求不重复建库，创建后可查询、权限正确，失败能恢复。对照预定义节点方案；若自治组织效果不佳，保留实验功能并如实报告，不让它阻止核心版本展示。

## 7. 现有 LabInsight 的复用与时间版本场景

analysis.py 保留纯统计；rules.py 作为规则节点后端；tools.py 接到节点工具；agent.py 复用工具循环并增加通用路由。避免第一步全仓库重写，先包一层接口。

历史规则应用验证保留：实验记录增加 experiment_time，规则表保存版本与 effective_from；选择当时生效的最新版本，时间区间 [生效时刻,下一版本时刻)。无时间/无规则记录不可判定，单独报告。

A-v1 阈值 80、A-v2 阈值 85，更新前后的 82 判定不同；指定版本重评标记模式。合格率分母为可判定有效数，为零返回 null。展示来源与版本。该应用检验精确事实版本、时间查询及结构化/文档混合访问，不作为存储框架的硬编码特例。

## 8. 工程结构与交付

建议在现有目录内逐步增加通用模块，例如 nodes/（协议与节点）、network/（接口与遍历）、backends/、memory/（归档/摘要/上下文），实际命名在实现时按需要选择。保持 labinsight 与 CLI 可用，不为每个概念提前创建空文件。

用 SQLite 持久化节点配置、接口、结构化事实、事件/状态；文档保留文件与索引。提供依赖清单、.env.example、初始化与迁移、固定模拟种子、清晰错误和脱敏日志。

CLI 为主，后期简单展示界面显示节点/连接、查询范围、访问路径、记忆更新、原文证据和回答；可导出报告。不开发生产级分布式事务、自建存储引擎、多用户登录平台或模型训练。

## 9. 评估与验收

### 9.1 网络确定性测试

单节点、空组合节点、单向/双向强接口、弱接口、混合链、环与共享后继；local/integrated/federated 范围；读/写/只写权限；过滤和转发；重复结果；重启恢复；预算截断；同名工具；写入归属与优先级。

预期范围和权限由小图手工给定。强合并在声明条件下，从不同入口返回同一数据集合；权限越界与死循环必须为零。

### 9.2 记忆与检索评估

约 40～60 个固定序列/问题：精确信息记忆、更正与历史查询、多轮摘要、任务恢复、文档证据、无证据、跨节点混合、外部范围和冲突。固定数据快照，开发/测试分开。

对照全部聊天历史、全部向量存储、人工固定分类、自动归档/路由；另比较有/无子 Agent。相同模型和问题集，记录事实取回正确率、旧值误用率、路由正确率、摘要关键约束遗漏率、Recall@k、引用支持率、权限违规、延迟和 token 成本。

精确查询和权限确定性用例全部通过；数值/版本正确率及 RAG Recall@5 可分别设为至少 95%/90% 的目标，但报告真实样本数和实测值，不把目标当成果。更复杂的路由若无收益，解释原因。

### 9.3 最终演示

输入模拟联系方式、长手册和开发讨论 → 自动存入已有节点 → 扩大查询范围查外部资料 → 更正联系方式 → 后续用新值且可查旧值 → 新会话恢复任务 → 展示双向强接口与环去重。LabInsight 再演示一个统计/规则版本混合查询。最后才演示按计划创建新节点。

## 10. 实施阶段与下一步

按阶段验收推进。原先累计约一个月的求职准备周期优先交付核心版，完整自治功能所需时间另评估，不承诺压进同一周期。

| 阶段 | 工作 | 完成标志 |
|---|---|---|
| 1 节点协议 | 明确数据类型、结果结构、直接调用；适配实验记录/规则；做空组合节点 | 无模型也能统一查询，原工具仍可运行 |
| 2 网络与权限 | 强弱接口、三种范围、环去重、来源、写入路由与持久化 | 手工小图范围和权限全部正确 |
| 3 记忆核心 | 精确事实版本、原始事件、摘要/任务、更新失效；写入计划进入已有节点 | 连续输入/更正/恢复流程可复现 |
| 4 RAG 与上下文 | 文档语料、基线、向量检索、权限/版本过滤、预算组装、可选子 Agent | 原文可引用，混合查询正确，公开比较结果 |
| 5 应用和交付 | LabInsight 时间规则验证、固定评估、界面/日志、环境复现 | 核心版可演示，有真实指标与局限 |
| 6 最后实现 | Agent 自主创建节点、迁移和接口组织 | 按计划、幂等、权限不扩大、失败可恢复 |

下一次具体开发从阶段 1 开始：先定义一个小的 Node 协议和 NodeResult，把现有实验规则查询封装为第一个数据节点，再做一个无本地数据的组合节点。暂不进行自动建库、全面包名迁移或大规模资料生成。
