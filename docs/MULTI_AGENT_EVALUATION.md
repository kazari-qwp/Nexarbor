## 建议任务：hone

目标是实现 CSV 到嵌套 JSON 的 Python 包与命令行工具，支持自定义分隔符、给定或推断结构、文件及标准输出。需求声明核心依赖均为 Python 标准库；原架构包含转换核心、CSV 工具、JSON 工具及包入口，存在真实模块依赖。我的判断是它比阅读时间计算任务更适合观察接口协商与集成，也能控制首轮成本。

来源：[需求](https://github.com/open-compass/DevEval/blob/main/benchmark_data/python/hone/docs/PRD.md)、[配置与测试入口](https://github.com/open-compass/DevEval/blob/main/benchmark_data/python/hone/repo_config.json)。官方完整评测环境提供 Docker；本机 Windows 可运行性尚未验证。hone 的配置中测试命令与标注目录存在不一致，准备阶段应核对实际文件并让参考实现通过固定的测试命令，记录任何环境适配，之后冻结评分脚本与数据。

## 执行步骤

1. 固定上游 commit、任务文件及测试文件的版本。建立评测目录和独立参赛工作区，将参考实现及评分测试保留在评测环境。成员只接收需求、架构、接口资料和允许的输入样本；不提供参考实现及标准答案。各轮实验使用同一材料。
2. 先运行参考实现确认评测环境可用，再在空实现上确认测试能识别失败。记录测试用例总数、固定命令及环境版本。环境问题先解决再开始计时。
3. 根发起任务。讨论组可先制定方案，再创建 4 人 decentralized_group，根据目标与验收标准自主认领、协商、实现、自测、提交及整合。不给成员预先指定模块分工。
4. 建议初次执行预算为 30 分钟，每成员最多 100 次模型请求；模型沿用前次 thinking 配置、500k 上下文、50k 最大输出，实际 token 用量与费用单独记录。预算是测试设置，正式执行前可调整。
5. 全体成员验收完成后，冻结共同工作区的提交；使用独立评测环境对该提交运行上游验收及单元测试，分别报告通过数、总数、异常与超时。成员的完成共识是收尾事件，最终是否成功由独立评分决定。
6. 观察至少两个成员是否提交并整合了有效修改、是否发生有证据的接口协商或交叉验收、根是否收到且能读取组级成果。保存会话、工具轨迹、费用、提交图及最终产物。这些过程指标帮助解释结果，不以消息数量代替成果。
7. 首轮用于确认端到端链路。若要判断多 Agent 是否带来收益，再增加单 Agent 对照：相同输入、权限、模型、全队总 token/费用上限，重复至少 3 次，同时比较质量、耗时与费用。单次成功不能证明性能提升。
